# 管理器包名迁移说明：`com.sukisu.ultra` → `com.yufeng.sukisu.ultra`

## 一句话结论

新版管理器 APK 的包名从 `com.sukisu.ultra` 改为 `com.yufeng.sukisu.ultra`，**签名证书不变**。

- **老用户**最省事：装新版 → 卸旧版 → 重启，内核会凭签名自动认主新版（见 B-1）。不想有任何失权窗口，再走 B-2 用「动态管理器」先交接。
- **全新用户**：只刷官方内核 + 官方管理器，再用「动态管理器」把本项目的 app 加为受信管理器，不刷本项目内核也能全功能使用（见 A）。

## 1. 背景

原包名与官方 SukiSU 管理器**完全相同**，但签名不同。Android 不允许同包名不同签名的两个 APK 共存，所以想装本项目管理器就必须先卸载官方管理器；而卸载官方管理器后，本项目的 app 又拿不到管理器权限（内核认的是被卸载掉的那个 UID），陷入死循环。

改包名后两个管理器可以共存。**签名绝对不能换**：内核靠编译进自身的签名哈希（`EXPECTED_HASH`）判断谁是管理器，换签名等于让所有"自动接管"路径失效，且无法自愈，只能重刷内核。

## 2. 必须先理解的四个机制

| 机制 | 规则 | 对迁移的意义 |
| --- | --- | --- |
| 管理器身份判定 `is_manager()` | 只查内核记录的 `ksu_manager_appid` 与"动态管理器"登记表，**不看包名、不验签名** | 光换包名不会自动获得身份，必须让内核重新认可一次 |
| 认主（crown） | 用编译期宏 `KSU_PACKAGE_NAME` 匹配系统里已安装的包，并校验该 APK 的签名哈希是否等于内核里的 `EXPECTED_HASH` | 内核只"首选"这一个包名 |
| 签名 fallback | 当 `KSU_PACKAGE_NAME` 那个包**没装**时，内核扫描 `/data/app`，把**任何签名哈希匹配 `EXPECTED_HASH` 的 APK**（不管包名）认作管理器 | 这就是"卸载旧包名后新包名能自动接管"的原理，前提是同一个签名证书 |
| 动态管理器 | 在现有管理器里把另一个 app 登记为额外受信管理器（包名 + UID + 签名），存于 `/data/adb/ksu/.dynamic_managers`，最多 **16 条**，有独立开关且默认关闭 | 立即生效、无空窗，是不想有失权窗口时的路径；登记的是该 app **当时**的签名哈希，换签名后条目失效需重建 |

另有一条：app 只有在 `!isManager && rootAvailable()` 时进入**预览模式**。此时首页提示"未检测到 SukiSU 内核。当前已有 root 权限，页面以预览模式打开；内核相关功能不会生效。"——模块管理（`su -c ksud`）、自定义模块仓库、boot 备份仍然可用，超级用户管理、App Profile、SusFS、KPM 等内核级功能不可用。模块相关命令只需要 root，不需要管理器身份。

## 3. A. 全新用户（从没装过任何东西）

前提：**官方内核必须是带"动态管理器"功能的较新版本**。旧内核没有这个能力，只能改刷本项目内核（刷完直接就是管理器，无需再登记）。

1. 刷官方 SukiSU 内核（LKM / GKI 方式按官方说明），**不要**刷本项目的 LKM 模块。
2. 安装官方 SukiSU 管理器，打开确认首页正常、不处于预览模式。
3. 安装本项目新版管理器（`com.yufeng.sukisu.ultra`）。此时它显示"未检测到 SukiSU 内核…预览模式"，属正常。
4. 在官方管理器里打开「动态管理器」页面，开启「启用动态管理器」。
5. 点「添加管理器」，选择 `com.yufeng.sukisu.ultra`，核对包名 / UID / 签名后授权。授权即时生效，不需要重启。
6. 杀掉新版 app 的后台再重开（或下拉刷新）。首页不再出现预览提示，即已成为管理器。
7. 之后日常使用新版 app。官方管理器可留可卸：即便卸载，`/data/adb/ksu/.dynamic_managers` 里的条目仍在，新版身份保留；此外因签名一致，卸载官方管理器后 fallback 也会继续认主新版。

## 4. B. 老用户（已刷本项目内核 + 旧版管理器）

现状：内核为本项目版本，管理器为 `com.sukisu.ultra`。目标：换成 `com.yufeng.sukisu.ultra`。

两条路，任选一条。都要先装新版 APK，区别只在于**卸旧包之前有没有先把新版登记进动态管理器**：

| 方案 | 步骤 | 失权窗口 | 适合谁 |
| --- | --- | --- | --- |
| **B-1 直接卸旧包** | 3 步 | 有（一次重启的时间） | 想省事，绝大多数人走这条 |
| **B-2 动态管理器交接** | 8 步 | 无 | 在乎全程可用的，或 B-1 失败后再走 |

### B-1 最省事：装新版 → 卸旧版 → 重启

原理：旧包卸载后，内核按 `KSU_PACKAGE_NAME` 找不到它，转入签名 fallback，扫 `/data/app` 把签名匹配 `EXPECTED_HASH` 的 APK 认作管理器 —— **不看包名**，所以新包自动接上。

1. 前提自查，三条都满足再动手：
   - 本项目内核是**较新**构建，含签名 fallback。很久以前刷的老内核可能没有这段逻辑，卸载后不会自动接管。
   - 签名未变。本次迁移沿用原 keystore，正常满足。
   - 手边留着**旧版 APK**（或能随时从 Release 下回来），万一要回滚。
2. （建议）在旧管理器里做一份 boot 备份，出问题可回滚。
3. 安装新版 APK（`com.yufeng.sukisu.ultra`）。包名不同，不会覆盖旧版，两者共存。此时打开新版会显示预览提示，属正常。
4. 卸载旧版 `com.sukisu.ultra`。
5. 重启手机。
6. 打开新版，首页不再出现"未检测到 SukiSU 内核"提示 → 迁移完成。

**失败怎么办**（重启后新版仍是预览模式）：

- 装回旧版 APK。内核会重新 crown 它（包名匹配 + 签名匹配），旧管理器身份立刻恢复，然后改走 B-2。
- 若连装回旧版也拿不到身份，说明签名与内核里的 `EXPECTED_HASH` 不符，只能重刷用当前签名编译的内核。

### B-2 零空窗：用动态管理器先交接

1. （建议）先在旧管理器里导出一份 boot 备份，出问题可回滚。
2. 安装新版 APK，与旧版共存。
3. 打开**旧版**管理器（此刻只有它持有 manager 身份）。
4. 进入「动态管理器」，开启「启用动态管理器」。
5. 点「添加管理器」，选择 `com.yufeng.sukisu.ultra`，核对包名 / UID / 签名后授权。权限**立即生效**，无需重启。
6. 打开新版 app，确认首页没有"未检测到 SukiSU 内核"提示，且能正常进入超级用户、模块等页面。
7. 卸载旧版 `com.sukisu.ultra`。卸载前若「动态管理器」里仍有旧版的条目，先点「移除管理器」清掉，再卸载。
8. 重启一次，再打开新版确认仍是管理器（验证条目已持久化、内核重新加载正常）。

关键约束：新包名必须与内核编译时写入的 `EXPECTED_HASH` 同一签名，否则 fallback 永远认不上，只能重刷内核。

## 5. 风险与注意事项

| 项 | 后果 | 怎么做 |
| --- | --- | --- |
| 换了签名证书 | 内核 `EXPECTED_HASH` 不匹配 → 认主和 fallback 双失效；已登记的动态管理器条目哈希也对不上。**永久失权，无法自愈** | 只能重刷用新签名哈希编译的内核，再重新登记条目。所以本次迁移必须沿用原 keystore |
| 动态管理器开关默认关闭 | 不加开关，加进去的条目不会被使用，新 app 依然没有身份 | 每次「添加管理器」前先确认「启用动态管理器」是开的 |
| 上限 16 条 | 满了之后「添加管理器」失败，新 app 无法获得身份 | 先移除不用的条目再添加 |
| 新旧共存期间谁是"默认管理器" | 内核只认一个 `ksu_manager_appid`：只要 `com.sukisu.ultra` 还装着，它就是 `KSU_PACKAGE_NAME` 命中的首选；新版的身份来自动态管理器条目。"装了就算管理器"是错的 | 走 B-2 时，确认新版可用后再卸载旧包名 |
| 老内核没有签名 fallback | B-1 依赖内核在找不到 `KSU_PACKAGE_NAME` 时扫 `/data/app` 按签名认主。很老的构建没这段逻辑，卸载旧包后新版不会自动接管 | 先按 B-1 失败处理装回旧版恢复身份，再走 B-2；或直接刷最新内核后重来 |
| `.dynamic_managers` 条目残留 | 卸载 app 不会清条目：白占 16 条配额，且同包名条目可能阻碍重新添加 | 先在「动态管理器」里对该条目点「移除管理器」，再卸载 app |
| 两个管理器同时有身份 | 都能改模块、授 root，容易互相覆盖配置 | 迁移完成后只保留一个 |

## 6. 如何验证自己是否已成为管理器

- **看首页**：出现"未检测到 SukiSU 内核。当前已有 root 权限，页面以预览模式打开；内核相关功能不会生效。"→ 没有 manager 身份。
- 首页无该提示，且超级用户、模块等内核相关页面能正常打开 → 已是管理器。
- 交叉验证：在旧 / 官方管理器的「动态管理器」页，「已授权管理器」列表里能看到 `com.yufeng.sukisu.ultra` 及其 UID、签名哈希。

## 7. 常见问题排查

1. **装不上，提示"应用未安装"或签名冲突**：系统里还有同包名 `com.yufeng.sukisu.ultra` 的残留（可能是不同签名的测试包）。到系统设置里卸载该包名残留后再装；若提示的是 `com.sukisu.ultra` 冲突，说明装成了旧包名版本，换用新包名 APK。
2. **装上了但功能都是灰的**：处于预览模式，没有 manager 身份。按 B-1 卸掉旧包重启，或按 A / B-2 把它登记进动态管理器。
3. **B-1 卸载旧包后失权了**：先装回旧版 APK 把身份救回来（内核会重新 crown 它），再走 B-2。若装回旧版也不认，基本可判定签名与内核 `EXPECTED_HASH` 不一致。
4. **动态管理器里加了，但新 app 没生效**：依次查——「启用动态管理器」是否真的打开；加完后是否杀进程重开过 app；条目里的包名 / UID 是否与当前安装实例一致（卸载重装后 UID 会变，需先「移除管理器」再重新添加）。
5. **重启后又变回预览模式**：条目没真正落盘或被清掉，检查 `/data/adb/ksu/.dynamic_managers` 是否存在且内容完整；内核过旧不支持该文件时，改用 B-1 路径（卸载旧包名 + 重启），或刷较新内核。

## 8. 构建侧：包名只有一个来源（维护者看这里）

包名默认值**只**定义在仓库根的 `manager-package.properties`，其他构建路径一律从它派生，不允许再各写一份字面量：

| 消费方 | 用法 |
| --- | --- |
| `manager/app/build.gradle.kts` | 读 `KSU_MANAGER_PACKAGE_NAME` / `KSU_MANAGER_PACKAGE_NAME_PR` → `applicationId` |
| `kernel/Kbuild`（`include kernel/manager-package.mk`） | 同两个键 → 编译期宏 `KSU_PACKAGE_NAME`；`KSU_IS_PR_BUILD=1` 时取 `.pr` 键 |
| `userspace/ksud/build.rs` | 同两个键 → `env!("KSU_PACKAGE_NAME")` |
| `.github/workflows/ksud.yml` | 只声明 `KSU_IS_PR_BUILD=1`，不写包名 |
| `.github/workflows/build-manager.yml` | 编译前跑一致性闸门 `verify-package-name` |

改包名只改这一个文件，且必须保持 `KSU_MANAGER_PACKAGE_NAME_PR == KSU_MANAGER_PACKAGE_NAME + ".pr"`。改完跑：

```bash
python3 scripts/check_manager_package.py --gradle
```

它会断言三件事逐字节相同——文件本身的值、`make` 求出的内核侧取值、Gradle 真实 `applicationId`；同时检查没有任何构建文件重新写死包名字面量。CI 里同一个脚本是编译前的硬闸门，不一致直接 fail，不会产出"能装但拿不到 manager 身份"的包。

一次性覆盖：`-PKSU_PACKAGE_NAME=<package>`（Gradle）和 `make KSU_PACKAGE_NAME=<package>`（内核）仍然优先，用于临时构建；不要把它写进仓库。

签名证书（`secrets.KEYSTORE`、`EXPECTED_HASH`、`apksign {}`）与这个文件无关，**不要**为了改包名去动它。
